# Runtime dependencies for the vva-agent Lambda container image.
#
# A deliberate subset of requirements-langgraph.txt, and the subtraction IS the
# point: this list has no torch, no sentence-transformers and no transformers.
# Those three are ~2 GB, and on Lambda they are not merely large — billing is
# memory x wall-clock, so the ~20 seconds a turn spends waiting on DeepSeek is
# 20 seconds of paying for a PyTorch that is doing nothing. Embeddings run on
# onnxruntime instead (EMBEDDING_BACKEND=onnx); see shared/onnx_backend.py.
#
# Measured, not guessed: import langgraph_agents.api.main:create_app in a clean
# interpreter and diff sys.modules, the same technique described in
# infra/lambda/crud_api/requirements.txt. Two findings from that run:
#
#   * `transformers` IS reachable — langchain_core/language_models/base.py does
#     `from transformers import GPT2TokenizerFast` — but it is wrapped in
#     try/except ImportError with a `_HAS_TRANSFORMERS = False` fallback. All it
#     gates is get_token_ids()/get_num_tokens(), which this codebase never calls
#     (0 hits across agenticRAG/); token counts come from the LLM response. So
#     omitting it costs nothing and saves the torch chain behind it.
#   * `mcp` and `langchain-mcp-adapters` are imported at MODULE level by
#     mcp/client.py, so they ship even though ENABLE_MCP=false on this image.
#     Leaving them out would fail at import, not at first use.
#
# Versions track requirements-langgraph.txt. When that file moves, move this
# one: an image running a different FastAPI than local development is a bug that
# only appears after deploy.

# leaves it out because "the Lambda runtime ships it". That reasoning does not
# carry over: this image is built on a plain python base, not on
# public.ecr.aws/lambda/python, because the Lambda Web Adapter takes the runtime
# interface role and the AWS base image's own runtime client would contend with
# it. No AWS base image, no preinstalled boto3.
#

# surface at the first request, not at INIT.

# 06/07/2026 — Latency optimization #1-4 (K spec + subagent impl)

## Bối cảnh
Real benchmark (29 requests) showed 100% of cost is LLM (DeepSeek) calls, with heavy p90/max
tail variance (planner p90 24.4s/max 37.8s, synthesizer p90 30.1s/max 55.4s) and retriever
waste: duplicate same-tool `tool_calls` in one round (`[kb_search, kb_search]`, 8x observed).
K wrote spec `docs/fixes/latency-optimization-1234.md`; subagent implemented + tested.

## Thực hiện (subagent)

**#1 — Prompt-cache observability** (`agenticRAG/langgraph_agents/llm.py`)
- Added `extract_cache_tokens(ai_msg)` (llm.py:~199-241): best-effort read of
  `response_metadata["token_usage"]["prompt_cache_hit_tokens"/"prompt_cache_miss_tokens"]`
  (DeepSeek extension fields), falling back to `usage_metadata.input_token_details`. Never
  raises — returns `(None, None)` if absent.
- Wired into `node_complete` logs for planner (`nodes/planner.py:323-334`), retriever_agent
  (`nodes/retriever_agent.py:237-254`), synthesizer (`nodes/synthesizer.py`, near end of
  `synthesizer_node`) as `cache_hit_tokens`/`cache_miss_tokens`.
- Planner needed `with_structured_output(..., include_raw=True)` (was parsed-only) to get a
  raw `AIMessage` to read telemetry from — added a small `_unpack()` shim so it still accepts
  a bare `PlanOutput` return (keeps old test-mock style compatible).
- No prompt restructuring (per spec — already optimal, static string).

**#2 — Timeout/retry + Gemini fallback** (`llm.py`, `nodes/planner.py`, `nodes/synthesizer.py`)
- `llm.py`: `get_chat_model()` now passes `timeout=` (fast roles 20s, heavy/synthesizer 35s,
  centralized via `_timeout_for_role()`/`_HEAVY_ROLES`) and `max_retries=1` to `ChatOpenAI`.
- `llm.py`: new `get_fallback_chat_model(role)` (`@lru_cache`), builds `ChatGoogleGenerativeAI`
  (`gemini-2.0-flash` fast / `gemini-2.5-pro` heavy) from the first key in comma-separated
  `GEMINI_API_KEYS`; returns `None` if unset (graceful, not a startup error).
- `planner.py` / `synthesizer.py`: on primary-call exception, attempt ONE fallback call before
  falling through to the existing safe-fallback/error logic. Success → `llm_fallback_used: true`
  log line + normal return; failure/unavailable → unchanged existing error path. Synthesizer
  fallback doesn't stream — emits one `writer({"content": final})` chunk to preserve the SSE
  `token` contract.

**#3 — Bound output size** (`llm.py`, `nodes/synthesizer.py`)
- `get_chat_model()` now passes `max_tokens=` (fast roles 512, heavy/synthesizer 1024).
- Synthesizer prompt (`_SYNTHESIZE_TASK` in `nodes/synthesizer.py`): "Keep under 500 words
  unless the topic requires detail" → "Keep under 350 words. Do not pad or repeat safety
  disclaimers — state each once."

**#4 — Dedupe retriever tool_calls** (`nodes/retriever_agent.py`)
- New `_dedupe_tool_calls(tool_calls)` — drops exact `(name, frozenset(args.items()))`
  duplicates, keeps first occurrence; same-name-different-args calls both kept (legitimate
  parallel search). Wired into `retriever_agent_node` right after `tool_calls = getattr(ai_msg,
  "tool_calls", []) or []`; mutates `ai_msg.tool_calls` in place (direct pydantic assignment
  works — no `object.__setattr__` needed, verified) before returning, so `ToolNode` only
  executes the deduped set. Logs `tool_calls_deduped: <removed_count>` in `node_complete` only
  when > 0.

## Design choices not fully pinned by spec (simplest-consistent picks, noted for K review)
- Planner's `with_structured_output` switched to `include_raw=True` — spec didn't call this out
  explicitly but it's required to have an `AIMessage` to read cache telemetry from for #1;
  added a shim so old bare-`PlanOutput`-returning test mocks still work.
- `_CACHE_HIT_KEYS`/`_CACHE_MISS_KEYS` in `extract_cache_tokens` also check generic
  `cache_read_input_tokens`/`cache_creation_input_tokens` names (Anthropic-style) as a second
  fallback after DeepSeek's exact field names — costs nothing, slightly more future-proof.
- Fallback models get the SAME timeout/max_tokens as the primary role's DeepSeek call
  (`_timeout_for_role`/`_max_tokens_for_role` reused) — not specified, seemed the least
  surprising default.

- Read all 4 diffs line-by-line against the spec. `AIMessage.tool_calls` direct-assignment
  claim (#4) verified independently (`python -c` repro) — correct, no `object.__setattr__`
  needed. Planner's `include_raw=True` shim verified safe: the pre-existing `if plan is None`
  handler (originally for "breaker returns None") already correctly catches the new
  silent-parse-failure shape — no gap.
- Re-ran full unit suite myself: **259 passed**, 0 regressions. Re-ran
  `test_fix_latency_1234.py` alone: **28/28 passed**.

**Found + fixed 2 real issues during review (not caught by unit tests, since they mock the
LLM boundary):**

1. **Synthesizer streaming + fallback double-write bug** — if the primary DeepSeek stream
   emits some tokens via `writer()` (live SSE, independent of this function's return value —
   see `api/main.py`) and THEN fails mid-generation (now newly possible with the #2 timeout),
   the except-block fallback would append a full second answer on top, producing a garbled,
   duplicated-looking response in the browser. Fixed: skip the fallback attempt entirely if
   `final` (accumulated primary content) is already non-empty when the exception fires —
   fall through to the existing clean error path instead of compounding partial + fallback
   output. `nodes/synthesizer.py`, except-block guard `already_streamed`.
2. **Gemini fallback retry storm** — `get_fallback_chat_model` didn't set `max_retries` on
   `ChatGoogleGenerativeAI`, so google-genai's SDK default kicked in: exponential backoff
   retries on 429 (observed live: 5 retries, 1.3s→2.9s→4.97s→8.74s→16.8s ≈ 36s) before
   giving up — defeating the point of a fast "one-shot" fallback, and making the worst case
   (primary timeout + fallback retry storm) worse than having no fallback at all. Fixed:
   `max_retries=0` on the fallback client. `llm.py`, `get_fallback_chat_model`.

**Live-tested end-to-end** (backend restarted with new code, real request fired against
:8000): DeepSeek is currently **out of balance** (`402 Insufficient Balance` — account/billing
issue, not a code bug; recurring — happened once before this session per STATUS.md) and Gemini
fallback is at **quota 0** (free-tier exhausted) — a genuine double-failure scenario, better
than anything a mock could exercise. Confirmed:
- Fallback cascade fires correctly (DeepSeek fails → Gemini attempted → also fails → falls
  through to existing safe error path) — no crash, no infinite hang, graceful Vietnamese
  error message reaches the user via `error_handler`.
- After the `max_retries=0` fix: planner `node_failed` dropped **40778ms → 4495ms**;
  synthesizer `node_failed` **1052ms**. Confirms the fix works, not just in theory.

## Follow-up (same day) — DeepSeek balance restored, full happy-path live benchmark

Owner topped up the DeepSeek account. Started Docker (postgres/redis/searxng), restarted
backend, fired 4 requests (greeting / kb-query / web-query / kb-query-2) against real
DeepSeek.

**Found + fixed a 3rd real issue (crash, not in original spec):** the first kb-query request
**crashed the backend process twice** (silent death, no traceback — OS-level kill under memory
pressure) at the exact moment `Loading pretrained SentenceTransformer` logged **2-3 times
simultaneously**. Root cause: `E5EmbeddingService.model` (`shared/embedding.py`) is a lazy
singleton with an **unguarded check-then-act race** (`if self._model is None: ... self._model
= SentenceTransformer(...)`, no lock) — its own docstring claimed "thread-safe" but that only
covered `encode()`, not the lazy-load itself. `aembed_query`/`aembed_passage` run this via
`asyncio.to_thread`, so when the retriever fires multiple `kb_search` tool_calls in parallel
(a real, correct pattern — e.g. `["kb_search", "kb_search", "kb_search"]` with 3 different
queries, correctly NOT deduped by fix #4 since they're not exact duplicates), each concurrent
call raced into the same unguarded load, each independently constructing a full
`SentenceTransformer` — N simultaneous loads spiking peak memory (3× in the observed crash) —
OOM-killed the process. **Fixed with a `threading.Lock` + double-checked locking** in
`shared/embedding.py` (`_load_lock`, added in `__init__`, guards the one-time load only — every
call after the first takes the fast unlocked path). This is a stability/thread-safety fix, NOT
a removal of the lazy-loading behavior itself (explicitly out of scope per Owner) — the model
still only loads on first use; concurrent first-uses now serialize instead of racing.
- Verified with a synthetic concurrency test (5 threads racing `.model`, mocked
  `SentenceTransformer`): **1 construction** for 5 concurrent callers (was N before the fix).
- Verified live: re-fired the exact request that crashed the backend twice — succeeded (200,
  54s cold-load-then-serialize), backend process stayed alive, `/health` still 200 afterward.
- Full unit suite re-run after this change: **259 passed**, 0 regressions.

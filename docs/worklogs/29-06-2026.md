# Kimodo CI/CD & Production Design
**Ngày:** 29/06/2026

Báo cáo tổng kết quá trình chuyển đổi kiến trúc dự án Kimodo từ môi trường Research sang Production Inference, chuẩn bị cho hệ thống CI/CD và triển khai trên AWS.

---

## 1. Những gì đã hoàn thành (Execution Summary)

* **Tách bạch luồng dự án:** Tạo nhánh `kimodo/inference` độc lập để tập trung tối ưu hóa cho Production, không làm ảnh hưởng đến môi trường Training/Research hiện tại.
* **Cắt giảm Dependency (Diet for Production):** 
  * Loại bỏ hoàn toàn các thư viện UI và đồ họa 3D không cần thiết cho inference (`gradio`, `trimesh`, `scenepic`, `viser`, `av`, `pillow`) khỏi core dependencies.
  * Cập nhật `pyproject.toml`, chuyển các UI dependencies sang nhóm `[project.optional-dependencies] (demo)` để lệnh `pip install -e .` mặc định không tải thư viện thừa.
  * Tạo file `docker_requirements_prod.in` chỉ chứa thư viện lõi (`torch`, `transformers`, `fastmcp`, `numpy`...).
* **Xây dựng kiến trúc Docker mới:**
  * Tạo `Dockerfile.prod` áp dụng chiến lược **Multi-stage build**.
  * Chuyển từ base image nguyên khối, khổng lồ (`nvcr.io/nvidia/pytorch`) sang base image tinh gọn (`nvidia/cuda:12.4.1-runtime-ubuntu22.04`).
* **Tích hợp AWS S3:**
  * Viết script `scripts/inference-entrypoint.sh` để tự động hóa hoàn toàn việc tải file bản quyền `SMPLX_NEUTRAL.npz` từ S3 bucket (`s3://eca-kimodo-assets`) vào container lúc runtime.
* **Build & Deploy:**
  * Đã biên dịch (compile) thành công file requirements.
  * Đã build thành công Docker image cho nhánh Inference.
  * Đã push image lên **AWS ECR** (`244203483654.dkr.ecr.us-east-1.amazonaws.com/kimodo:latest`).

---

## 2. Những quyết định đã chốt (Architectural Decisions)

* **Hardware & Compute:** Chốt sử dụng **EC2 g5.xlarge** (A10G - 24GB VRAM). Mode `TEXT_ENCODER_DEVICE=cuda` sẽ được kích hoạt. Cả Text Encoder (LLM2Vec) và Motion Model sẽ được nạp chung vào 1 GPU, tiêu tốn khoảng ~19GB VRAM (vừa vặn, tối ưu chi phí VRAM).
* **Quản lý Code Production:** Các file dành cho Production (Docker, Requirements, Scripts) sẽ có hậu tố riêng hoặc nằm hẳn trên nhánh `kimodo/inference` để bảo vệ mã nguồn Research gốc.
* **Chiến lược Model Storage:** Sẽ **KHÔNG** đóng gói 18GB model weights vào trong Docker Image, cũng như **KHÔNG** ưu tiên dùng EFS vì vấn đề độ trễ. Chiến lược được chốt là dùng đĩa gắn ngoài qua **Custom AMI / EBS Snapshot**.

---

## 3. Những gì sẽ làm tiếp theo (Next Steps)

* **Thiết lập CI/CD Pipeline:** Sử dụng GitHub Actions hoặc AWS CodePipeline để tự động trigger lệnh build `Dockerfile.prod` và push lên ECR mỗi khi có code mới merge vào nhánh inference.
* **Tự động hóa Model Baking:** Viết script/IaC (Terraform hoặc Packer) để tải trước (pre-download) cache của HuggingFace (~18GB) vào một ổ cứng ảo và tạo EBS Snapshot.
* **Cấu hình Infrastructure:** Viết cấu hình Launch Template cho cụm EC2 Spot. Launch Template này sẽ có nhiệm vụ:
  1. Yêu cầu Spot Instance mới.
  2. Tự động khởi tạo và gắn (attach) EBS Volume từ Snapshot chứa model.
  3. Kéo Docker image tinh gọn từ ECR về và khởi động MCP Server với thời gian cold-start tiệm cận 0.

---

## 4. Bài học rút ra (Lessons Learnt)

> [!TIP]
> **1. Tách bạch Research và Production là bắt buộc**
> Việc bê nguyên repo Research lên Production luôn dẫn đến lãng phí tài nguyên khổng lồ. Các công cụ visualize như Trimesh, Viser, hay Gradio bắt buộc phải cài kèm hàng đống system libraries (OpenGL, glibc). Bằng cách mạnh dạn gạt bỏ, dung lượng image giảm xuống hàng chục GB, thời gian build từ 1 tiếng chỉ còn vài phút.

> [!TIP]
> **2. Lựa chọn Base Image thông minh**
> Không nên phụ thuộc vào các image "all-in-one" tiện lợi (như NGC PyTorch container) cho môi trường Inference. Sử dụng Multi-stage build kết hợp CUDA Runtime thuần túy, kết hợp tự cài đặt PyTorch wheels là cách an toàn và nhẹ nhất.

> [!TIP]
> **3. MLOps: Tách biệt Code và Model Weights**
> Khi làm việc với LLMs/GenAI và Spot Instances, điểm nghẽn cổ chai lớn nhất là tải Model Weights (vài chục GB) chứ không phải là tải code. Việc nhồi nhét model vào Docker Image là anti-pattern. Tách luồng CI/CD thành 2 phần: **Luồng Code** (chạy qua Docker/ECR liên tục) và **Luồng Data/Weights** (chạy qua EBS Snapshot/AMI ít thay đổi hơn) là bí quyết để đạt được độ ổn định và tối ưu chi phí.

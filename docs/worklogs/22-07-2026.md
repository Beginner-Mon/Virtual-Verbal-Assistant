# 22/07/2026 — Gemini context caching (infra, currently inert on free tier)

## Bối cảnh
Owner: "cứ tạo đi" — build Gemini prompt caching để chuẩn bị cho tính năng tương lai
(user tự upload API key + chọn provider trước). Trước đó đã xác nhận DeepSeek cache tự động
nhưng Gemini thì không (test live: cùng prompt tĩnh gửi 3 lần, `cache_read` luôn = 0).

## Research trước khi code (tránh xây cái không dùng được)
- Verify bằng `genai.Client` thật: Gemini caching **không tự động** — phải tạo tường minh
  `CachedContent` (nội dung + TTL), tham chiếu qua `cached_content=` mỗi call sau.
- **Ràng buộc cứng**: dùng `cached_content` thì **không được** gửi `system_instruction`
  riêng — phải nằm sẵn trong cache.
- Thử tạo cache thật với đúng prompt planner (~1296 token) → **FAILED**:
  `429 TotalCachedContentStorageTokensPerModelFreeTier limit=0`. Đây là **giới hạn tier**
  (free-tier = 0 quota cache), không phải lỗi prompt nhỏ/code sai.
- `langchain_google_genai` có sẵn `create_context_cache()` (dùng thay vì tự viết raw API) và
  `ChatGoogleGenerativeAI.cached_content` chấp nhận cả constructor-time lẫn per-call.

## Quyết định phạm vi
- **Chỉ áp dụng cho `planner` fallback** — vì đó là chỗ duy nhất prompt tĩnh 100% (giống lý do
  DeepSeek cache ăn ~91% ở planner). `synthesizer` có evidence động chèn mỗi lần → cache không
  giúp gì, chỉ thêm round-trip vô ích — cố ý KHÔNG làm.
- **Tách rời "tra cứu" và "tạo cache"** để không lặp lại lỗi retry-storm đã sửa trước đây
  (fallback không được chậm hơn không-có-fallback):
  - `get_warm_gemini_cache()` — tra cứu in-memory, KHÔNG gọi mạng, an toàn gọi trong đường
    fallback trực tiếp.
  - `warm_gemini_cache()` — gọi API thật để tạo/tái dùng cache, **cố ý KHÔNG gọi tự động**
    từ đường fallback (tránh block latency) — chỉ gọi chủ động (startup hook/cron sau này).

## Thực hiện
`llm.py`: thêm `get_warm_gemini_cache`, `warm_gemini_cache`, `get_gemini_cached_chat_model`
(registry in-memory + TTL 1h, lock threading). `planner.py`: fallback path thêm nhánh thử
cached model trước (chỉ dùng nếu đã ấm sẵn), gửi CHỈ user-turn khi dùng cache (đúng ràng buộc
API). Khi cache chưa ấm (100% trường hợp hiện tại) → luồng y hệt trước, 0 thay đổi hành vi.

## Test
- 10 test mới (`TestGeminiContextCaching`, `TestPlannerUsesGeminiCacheWhenWarm`): lookup
  rỗng/còn hạn/hết hạn, tạo cache thành công (mock) + không gọi lại trong TTL, tạo cache thất
  bại → None không raise, thiếu API key → None, wiring planner đúng (chỉ gửi user-turn khi
  cache ấm). Full suite: **270 passed**, 0 regression.
- **Live thật (không mock)**: gọi `warm_gemini_cache()` với đúng prompt + key thật → bắt đúng
  lỗi 429 quota=0, trả `None`, KHÔNG có exception lọt lên trên. Xác nhận cơ chế degrade an
  toàn hoạt động đúng trên điều kiện lỗi thật, không chỉ mock.

## Giới hạn — nói rõ để không overclaim
**Không thể verify "cache thật sự được tạo + tái dùng + giảm latency"** — bị chặn hoàn toàn bởi
giới hạn free-tier (quota cache = 0), không phải do code. Cơ chế hiện tại **luôn inert** (không
kích hoạt) cho tới khi dùng key trả phí. Đây là hạ tầng sẵn sàng cho tính năng BYO-key tương
lai, không phải tối ưu latency đang có hiệu lực ngay bây giờ.

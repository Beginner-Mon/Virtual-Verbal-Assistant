## Problem Statement

User `a@gmail.com` (emailSub set, googleSub = null) clicks "Link Google" in Settings, selects wrong Google account `b@gmail.com`:

1. UI shows "Linked" despite server-side rejection → **stale Amplify token cache**
2. Cognito creates/link Google identity for `b@gmail.com` → **orphaned identity in Cognito**
3. Login page → "Continue with Google" → auto-sign-in via wrongly-linked `b@gmail.com`

---

## Root Cause

### `resource.ts:12` — `attributeMapping: { email: 'email' }`

During Google link flow, Cognito applies `attributeMapping` and **overwrites** the signed-in user's `email` attribute with the Google claim value:

```
User signed in: a@gmail.com (cognitoSub = SUB_A)
→ Google OAuth returns: email = b@gmail.com, sub = GOOGLE_SUB_B
→ Cognito mapping: email = 'b@gmail.com' (OVERWRITTEN)
→ request.userAttributes.email = 'b@gmail.com'
```

### Downstream cascade

1. PostConfirmation fires with `email = 'b@gmail.com'`
2. Queries DynamoDB `email-index` for `'b@gmail.com'` → **NOT FOUND** (record exists for `a@gmail.com`)
3. Creates **new** DynamoDB record: `{ email: 'b@gmail.com', googleSub: SUB_A }` (wrong)
4. Cognito links Google identity `GOOGLE_SUB_B` to the user
5. DynamoDB now has 2 records sharing same `cognitoSub`:
   - Record 1: `appUserId=UUID1, email='a@gmail.com', emailSub=SUB_A`
   - Record 2: `appUserId=UUID2, email='b@gmail.com', googleSub=SUB_A` (orphan)
6. Login page: user types `a@gmail.com` → lookup → `hasGoogle: true` → "Continue with Google" → Google auto-selects `b@gmail.com` (identity linked) → sign-in succeeds via wrong account

---

## Why Lambda triggers cannot fix this

| Trigger | Reason |
|---------|--------|
| `PreSignUp_ExternalProvider` | Only receives new identity info (`b@gmail.com`), no session of signed-in user (`a@gmail.com`). Cannot cross-reference original email. |
| `PostConfirmation` | Fires AFTER Cognito has already created/linked the identity and committed attributes. No rollback possible at this point. |

---

## Attempted fixes (rejected)

### 1. AuthGuard email mismatch check (original plan)

```typescript
tokenEmail = s.tokens.idToken?.payload?.['custom:email']  // → 'a@gmail.com' (user pool email, static)
linkingEmail = sessionStorage.getItem('linkingEmail')      // → 'a@gmail.com' (same value)
tokenEmail !== linkingEmail                                // → ALWAYS false
```

Flaw: both values reference the user pool user's email attribute, which never changes during linking. Self-comparison is a no-op.

### 2. Force-refresh token in AuthGuard (`fetchAuthSession({ forceRefresh: true })`)

Fixes stale Amplify token cache → UI shows correct `googleSub`. But does NOT prevent Cognito from creating/linking the Google identity on the server side.

### 3. Delete `preferred_username` from userAttributes

Breaks `CreateAccountPage.tsx` sign-up flow — `preferred_username` is how `displayName` travels from sign-up form → Cognito → PostConfirmation → DynamoDB. Cannot remove it from `userAttributes`, only from `attributeMapping`.

---

## Actual fixes applied

### 1. `auth/resource.ts` — Remove `email` from attributeMapping

```diff
  attributeMapping: {
-   email: 'email',
    emailVerified: 'email_verified',
    givenName: 'given_name',
    familyName: 'family_name',
+   preferredUsername: 'email',
  }
```

- Cognito no longer overwrites `email` during link → PostConfirmation sees correct `a@gmail.com` → finds existing DynamoDB record
- `preferredUsername` maps Google email as vessel for future email-mismatch detection if needed in PostConfirmation
- `preferredUsername` kept as `{ required: false, mutable: true }` — sign-up flow unchanged

### 2. `AuthGuard.tsx` — Force-refresh on link return

```typescript
if (linkingEmail) {
  const fresh = await fetchAuthSession({ forceRefresh: true })
  if (fresh.tokens) tokenSource = fresh
}
```

Replaces broken email-mismatch check. Fresh token reflects actual DynamoDB state via Pre-Token Generation Lambda.

### 3. `ProfileContent.tsx` — Revert `linkingPrevGoogleSub`

Back to original plan — no unnecessary state tracking in sessionStorage.

---

## Remaining gap

Current setup prevents DynamoDB corruption and Cognito overwrite, but the Google identity **is still linked** (`custom:googleSub` gets set if Google email matches). There is no pre-check that the Google account's email matches the user's email before the link.

Frontend pre-check via Google Identity Services popup (before `signInWithRedirect`) is the only place to catch email mismatch before Cognito processes the link. Requires Google OAuth client ID accessible in frontend.

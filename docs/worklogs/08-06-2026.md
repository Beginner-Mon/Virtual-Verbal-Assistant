## 1. CloudTrail concepts

### 1.1 Trail vs Event History

| | Event History | Trail |
|---|---|---|
| Setup | Automatic | Manual |
| Retention | 90 days | Unlimited (S3) |
| Event types | Management only | Management + Data + Insights + Network Activity |
| Cost | Free | Paid (first trail free for management events) |

Trail dùng cho: long-term audit log, compliance, CloudWatch Logs integration, EventBridge alerting.

### 1.2 4 loại events

**Management Events** — control plane operations: tạo/sửa/xóa AWS resource (CreateBucket, AttachRolePolicy, RunInstances). Volume thấp, trail đầu miễn phí.

**Data Events** — data plane operations: thao tác trực tiếp lên dữ liệu bên trong resource (S3 GetObject/PutObject, Lambda Invoke, DynamoDB GetItem). Volume rất cao, tính phí theo số lượng — nên filter chỉ bật cho resource cần thiết.

**Insights Events** — anomaly detection tự động trên management events. Phát hiện bất thường về API call rate và API error rate (VD: TerminateInstances tăng đột biến → credential compromise signal). Phải bật thủ công, tính phí riêng.

**Network Activity Events** — API calls đi qua VPC Endpoints (PrivateLink). Bổ sung context: VPC Endpoint ID, source VPC, cross-account calls. Relevant cho ECA vì Lambda chạy trong private subnet giao tiếp qua VPC Endpoints.

### 1.3 CloudTrail vs CloudWatch

| | CloudTrail | CloudWatch |
|---|---|---|
| Hỏi | *Who did what to this resource?* | *How is this resource performing?* |
| Góc nhìn | Audit / Security | Observability / Operations |

Cùng một Lambda invocation: CloudTrail thấy **ai gọi, từ đâu**; CloudWatch thấy **duration, memory, error**.

### 1.4 CloudTrail không theo dõi end user

CloudTrail luôn luôn track **IAM principals** (IAM User, IAM Role, AWS service, root account) — không bao giờ là application end user. Kể cả Data Events, người gọi API vẫn là Lambda execution role, không phải Cognito user đứng sau.

Để trace đến end user phải tự implement ở application layer — log `cognito_sub` kèm theo mỗi request trong Lambda.

**Ngoại lệ duy nhất (gián tiếp)**: Cognito Identity Pool cấp temporary AWS credentials thẳng cho end user qua `AssumeRoleWithWebIdentity` — lúc này CloudTrail ghi Cognito Identity ID có thể map ngược ra user. Tuy nhiên pattern này ít dùng trong production vì expose AWS credentials ra client.

### 1.5 CloudTrail với Cognito trong production

CloudTrail monitor **ai thao tác lên Cognito infrastructure**, không phải end user login:

- `AdminDeleteUser`, `AdminDisableUser` hàng loạt → insider threat / script tấn công
- `UpdateUserPoolClient` — OAuth scope bị mở rộng trái phép
- Lambda trigger bị swap sang function khác
- App Client lạ được tạo thêm
- `AssumeRoleWithWebIdentity` — ai được cấp AWS credentials từ Identity Pool

Kết hợp Insights Events có thể detect pattern bất thường tự động.

## 2. Cognito Google OAuth setup

### 2.1 Các khái niệm phân biệt

**User Pool Domain** — URL endpoint Cognito dùng để host Managed Login page. Bắt buộc khi có external IdP vì Google OAuth là browser redirect flow — cần một URL để redirect đến. Email/password login không cần vì toàn bộ xảy ra trong app qua Cognito SDK.

**Authorized Scope (tầng Google)** — scope Cognito xin từ Google: `openid email profile`. Cognito dùng để đọc thông tin Google account rồi map vào User Pool attributes. Không liên quan đến authorization trong app.

**Managed Login Branding** — bắt buộc phải tạo ít nhất 1 Style và assign vào App Client. Không phải chỉ là visual customization — đây là "toggle bật Managed Login cho App Client". Không có Style → 403 "Login pages unavailable".

**Setup Google trên Cognito (backend) vs UI (frontend)** — hoàn toàn tách biệt. Backend: tạo OAuth Client ID/Secret trên Google Cloud Console, add Google làm IdP trong Cognito, config scopes, attribute mapping — một lần duy nhất qua CDK/Console. Frontend: implement button `signInWithRedirect({ provider: 'Google' })` trong React — độc lập.

Google **không charge** cho OAuth — đây là Google Identity Services free API. Chi phí duy nhất là AWS Cognito MAU.

### 2.2 Account linking

Mặc định Cognito tạo 3 user riêng biệt nếu cùng email login bằng email/password, Google, GitHub.

**Security risk của auto-link**: Cognito tạo account ngay với `email_verified = false` trước khi user verify. Attacker có thể tạo unverified account với email của victim → nếu auto-link không check `email_verified` → Cognito link nhầm Google identity của victim vào account của attacker.

**Fix**: Dùng Pre Sign-up Lambda để tự kiểm soát — chỉ link khi `email_verified = true`.

**Spam unverified accounts**: Cognito tự xóa unverified accounts sau 7 ngày (configurable). Có thể thêm AWS WAF hoặc filter disposable email domains trong Pre Sign-up Lambda.

### 2.3 `amplify_outputs.json` OAuth config

```json
"oauth": {
  "domain": "eca-us-east-1.auth.us-east-1.amazoncognito.com",
  "scopes": ["email", "openid", "profile"],
  "redirect_sign_in_uri": ["http://localhost:5173/"],
  "redirect_sign_out_uri": ["http://localhost:5173/"],
  "response_type": "code",
  "social_providers": ["GOOGLE"]   ← array of strings, không phải object
}
```

## 3. AuthGuard 400 Bad Request debug

### 3.1 Sequence lỗi gặp phải

1. **"Login pages unavailable"** → Managed Login Branding chưa được tạo/assign vào App Client
2. **403** → Vẫn còn sau khi tạo Style nhưng chưa assign vào App Client
3. **400 Bad Request** tại `/login?client_id=...&logout_uri=...` → Amplify trigger cleanup flow trước login

### 3.2 Root cause của 400

```
GET https://eca-us-east-1.auth.us-east-1.amazoncognito.com/login?client_id=...&logout_uri=http://localhost:5173/
```

Amplify tự inject bước pre-login cleanup khi detect stale OAuth state — gọi `/login?logout_uri=...` để clear Cognito session trước khi bắt đầu flow mới. 400 xảy ra vì `logout_uri` không có trong **Allowed sign-out URLs** của App Client.

Tuy nhiên add sign-out URL gây ra vấn đề khác (load 2 lần) → không phải solution mong muốn.

### 3.3 `AuthGuard.tsx` logic bug

```typescript
// Sai — logic inversion
const [ready, setReady] = useState(!isAmplifyConfigured)
// Khi isAmplifyConfigured = true → ready = false
// → show loading spinner → lazy load Authenticator
// → trong window đó Amplify chưa có Authenticator để handle ?code= trong URL
// → trigger cleanup flow → 400

// Đúng
const [ready, setReady] = useState(false)
```

`useEffect` cũng cần fix:

```typescript
useEffect(() => {
  if (!isAmplifyConfigured) {
    setReady(true) // bypass mode
    return
  }
  Promise.all([
    import('@aws-amplify/ui-react'),
    import('@aws-amplify/ui-react/styles.css'),
  ]).then(([mod]) => {
    setAuthModule({ ... })
    setReady(true)
  })
}, [])
```

### 3.4 Amplify Authenticator UI vs Cognito Hosted UI

Dù dùng `@aws-amplify/ui-react` Authenticator (render trong app, không redirect ra ngoài), khi user click Google button Amplify vẫn **phải redirect qua Cognito OAuth endpoint** cho social login flow. Không tránh được — Managed Login Branding vẫn bắt buộc.

### 3.5 Tại sao session vẫn còn sau khi không có sign-out URL

Cognito session cookie tồn tại trên domain `amazoncognito.com` không bị clear dù refresh hay đóng tab. Amplify lưu tokens vào localStorage — reload app → Authenticator check localStorage → có tokens → vào thẳng app. Sign-out URL chỉ cần thiết khi gọi explicit `signOut()`.

## 6. Lessons learned

1. **CloudTrail theo dõi IAM principals, không phải end user** — mọi thứ liên quan đến user app phải tự implement ở application layer hoặc dùng Cognito logs.
2. **Managed Login Branding là bắt buộc** — không phải optional customization. Không có Style assigned → 403 bất kể config khác đúng hết.
3. **`social_providers` trong `amplify_outputs.json` phải là array** — `["GOOGLE"]` không phải `{ "google": "Google" }`.
4. **Logic inversion trong `useState(!isAmplifyConfigured)`** tạo race condition với OAuth `?code=` callback trong URL — Amplify không kịp handle trước khi trigger cleanup flow.
5. **Amplify Authenticator UI vẫn phải đi qua Cognito OAuth endpoint** cho social providers — không bypass được Hosted UI domain requirement dù UI render trong app.
6. **Auto account linking có security risk** khi email chưa verified — luôn dùng Pre Sign-up Lambda để kiểm soát điều kiện link.

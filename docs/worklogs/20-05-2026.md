# 20/05/2026 — N's Reviews: v2.1 (5 Runtime Fixes) + v2.2 (Hybrid Edge-Cloud)

## Summary

N provided second review of Plan v2, identifying 5 "hidden bottlenecks" that would break the system during real demo. K analyzed each, agreed on all 5 (with nuance on #2 and #5), and updated plan to v2.1.

---

## 1. N's 5 Objections + K's Responses

### Objection 1: Celery + WebSocket "Disconnect Trap"

**Problem**: User sends motion render request (takes ~60s), refreshes page at 30s. Old WebSocket dies, new one connects. Celery finishes at 60s → publishes to Redis Pub/Sub → nobody listening. User never receives result.

**K's verdict**: **Agreed 100%** — real production bug.

**Resolution**: Dual delivery — Celery writes result to both:
1. `task_result:{task_id}` in Redis (TTL 1h) — persistent fallback
2. Redis Pub/Sub channel — real-time delivery

On WebSocket reconnect with `session_id`:
1. Read `pending_tasks:{session_id}` → get active task IDs
2. Check `task_result:{task_id}` for each → push completed results immediately
3. Subscribe to Pub/Sub for still-running tasks

**Phase impact**: Added to Phase 3 (Celery Tasks).

---

### Objection 2: Aggregator Node is Redundant

**Problem**: LangGraph auto-merges state via `operator.add` / dict update. A dedicated node just for string concatenation adds overhead and graph complexity.

**K's verdict**: **Partially agreed** — pure string concat is unnecessary, but the node serves other purposes.

**Resolution**: Rename `Aggregator` → `Validator`. Expanded role:
- Validates sub-agent outputs are populated (not None/empty)
- Builds `raw_answer` with fallback if data missing
- Observability checkpoint — logs what all sub-agents returned before persona styling
- Drop if profiling shows >50ms overhead

**Phase impact**: Rename in Phase 2. Validation logic added.

---

### Objection 3: No Error Routing in Graph

**Problem**: Graph flow has no conditional edges for error handling. If Reasoning node times out (Claude API down), graph continues to Conversation with empty data → raw error shown to user.

**K's verdict**: **Agreed 100%** — design gap.

**Resolution**: Added error routing with 3 severity levels:
- `CRITICAL` (LLM/DB down): → `error_handler` node → `conversation` → END (graceful apology)
- `RECOVERABLE` (Retrieval timeout, DART down): skip failed node, continue with available data, warn user
- `IGNORABLE` (non-essential fail): log only

Added `ErrorSeverity` enum + structured error entries in `AgentState.errors`:
```python
{"node": "reasoning", "severity": "critical", "message": "Claude API timeout", "timestamp": "..."}
```

Added `error_handler.py` node to directory structure.

**Phase impact**: Error routing scaffold added to Phase 0 (must exist from day 1).

---

### Objection 4: Overly Optimistic Vendor Lock-in Claim

**Problem**: Plan claims "rewire to asyncio in 1-2 days" but LangGraph manages checkpointing, state persistence, and streaming APIs. These are deeply coupled.

**K's verdict**: **Agreed** — wording was misleading.

**Resolution**: Updated ADR-001 de-risk statement:

| Layer | Lock-in level | Rewire effort |
|-------|--------------|---------------|
| Business logic (node functions) | None | 0 days |
| Graph wiring (edges, routing) | Medium | 1 day |
| State persistence (checkpointing) | High | 2-3 days |
| Streaming (astream_events) | High | 1-2 days |
| **Total** | | **~1 week** |

Trade-off accepted: LangGraph provides features that would take 3-4 weeks to build from scratch.

**Phase impact**: Documentation only. No code changes.

---

### Objection 5: OOM Risk on 16GB RAM

**Problem**: PostgreSQL pgvector index building + DART render + Celery workers + potential Ollama = OOM crash on 16GB machine.

**K's verdict**: **Agreed on concern, corrected severity estimate.**

N overestimated vector data impact: 23.4k vectors × 384-dim × 4 bytes = ~34MB raw, ~70MB with IVFFlat index. Not the OOM culprit.

Real OOM risk: concurrent heavy services (DART 4GB + Ollama 6GB = already 10GB before anything else).

**Resolution**: Added RAM Budget (Section 3.4 in plan):
- PostgreSQL: 2GB hard Docker limit
- Redis: 512MB maxmemory
- Celery: 1GB (2 workers × 500MB max-memory-per-child)
- DART: 4GB
- Ollama: 6GB — **mutually exclusive with DART**
- **Rule**: Dispatch node checks active processes; DART task queued if Ollama loaded

**Phase impact**: Docker memory limits added to Phase 0.

## 4. N's v2.2 Proposal: Hybrid Edge-Cloud + Tool Upgrades

After v2.1, N proposed major deployment and tooling changes. K reviewed and responded.

### 4.1 Hybrid Edge-Cloud Deployment

**N's proposal**: Split infrastructure — Cloud (VPS + Supabase) for API/DB, Local (HP ProDesk 48GB RAM, RTX 3060) for heavy compute via Celery.

**K's verdict**: **Agreed on direction.** Corrected budget: $5 VPS (1GB RAM) insufficient for FastAPI + Redis. Recommended $10 VPS (2GB) or Supabase managed Postgres to offload VPS.

**Resolution**: Cloud = VPS $10 (FastAPI + Redis) + Supabase (PostgreSQL managed). Edge = HP ProDesk (Celery workers for Kimodo + VieNeu-TTS).

### 4.2 NVIDIA Kimodo (replaces DART)

**N's answer**: Kimodo is a complete replacement for DART. Supports kinematic constraints (joint angles, limb positions) — critical for physical therapy exercise accuracy. FastAPI wrapper inside Celery worker. Input: JSON `{prompt, constraints}`. Output: .mp4/.bvh → storage URL. Render: 5-10s.

**K's verdict**: **Accepted.** Joint angle precision is a clinical safety requirement. Added dedicated integration tests in Phase 3. Keeping DART code in `retired/` branch as fallback until Kimodo validated.

### 4.3 VieNeu-TTS-v2-Turbo-GGUF (replaces Coqui/ElevenLabs)

**N's answer**: Open-source HuggingFace model. GGUF format → CPU-only inference. Vietnamese-optimized with English code-switching. HP ProDesk 48GB RAM handles it easily.

**K's verdict**: **Accepted.** CPU-only = 100% GPU freed for Kimodo. No resource contention. Updated RAM budget — 48GB eliminates OOM concerns from v2.1.

### 4.4 SSE Replaces WebSocket (ADR-005 revised)

**N's proposal**: SSE (`text/event-stream`) for server→client streaming. REST POST for client→server queries. CDN-friendly, EventSource auto-reconnect.

**K's analysis**: SSE is better for hybrid edge-cloud — passes through CloudFront/Nginx natively, no WebSocket upgrade negotiation. Bidirectional not needed (user sends via REST POST).

**Owner's decision**: **Approved.** Reasons: CDN compatibility, built-in auto-reconnect, cleaner separation of concerns.

**Resolution**: ADR-005 revised. SSE + REST POST replaces WebSocket.

### 4.5 Approval Gate (Clinical Safety + Compute Saving)

**N's answer**: Use case is Clinical Safety Gate. AI streams exercise recommendation as text → user/therapist reads → if appropriate, clicks "Mô phỏng 3D" → only then GPU renders motion.

**K's design**: Gate handled **outside LangGraph** — graph runs to completion, streams text via SSE. Dispatch node stores motion payload in Redis `motion_pending:{request_id}`. User approval triggers `POST /render/approve/{request_id}` → Celery fires Kimodo task. Clean, no graph pause/checkpoint complexity.

**Resolution**: Approved. Added to Dispatch node + new REST endpoint.

### 4.6 Graceful Degradation (Worker Down)

**N's proposal**: If local Celery worker is offline (power out, maintenance), graph still returns text response with maintenance warning.

**K's verdict**: **Agreed 100%.** Dispatch node checks worker heartbeat. If down → RECOVERABLE error → text streams normally → "Mô phỏng 3D" button hidden → warning shown.

# 05-09-2026 — the personas ship, and three deploy faults that were hiding behind each other

> Previous session: [[03-09-2026]]. Plan: [[preferences-v3-plan]].

## Summary

Owner rewrote `personas/anne/vi.md`; `en.md` was rewritten against it, the
library was renamed from Ordinary to ECA everywhere it still mattered, and every
greeting stopped opening with an exercise. That part took twenty minutes.

Getting it to production took the rest of the session, and found three separate
infrastructure faults, two of which had been silently breaking every agent deploy
since **29-08**. The backend is live and verified. The frontend is not: Amplify
cannot assume its service role, and that one is with the Owner.

Roles stayed swapped — K implemented.

## What changed in the personas

**The library.** `anne/_core.md` had said ECA since the overlay split, but the
row the backend actually reads still said *"Retrieved results ARE Ordinary's
library"*. `preload_personas_from_db` fills the cache from `characters.persona`,
and that JSONB **shadows the markdown** — so the agent was citing a source no
grep in this repo could find. Fixed by syncing, not by editing.

"Ordinary Studio" stays on the About page. That is the company; only the library
was wrong.

**The greetings.** Twelve of sixteen prescribed an activity — *warm up, loosen
up, wind down, one relaxing stretch* — before the user had said a word. A
greeting is precisely the moment you cannot know that exercise is what someone
came for. They now follow `anne/vi.md`: name, then one open question. Bronya
keeps one symptom-led slot because for her that IS the open question.

The `(chat)` one-shot examples moved with them. Leaving *"what are we working on
today?"* there would have put the prescribing opener straight back into the
reply.

## `sync_personas_to_db.py` was blind where it mattered

`diff_sections` reports overlay changes under a composite **label** —
`"vi.examples"` — and the printer looked that label up as a **key**.
`persona.get("vi.examples")` is always `None`, so every overlay section printed:

```
vi.examples
  - (empty)
  + (empty)
```

Core sections printed correctly, which is exactly why it survived: the report
looked like it worked. The script exists so that nobody writes to
`characters.persona` blind, and it was failing at that, silently. Also taught it
to read a pre-overlay flat row as the `vi` overlay, so this migration's report
did not understate what it was replacing.

## Deploy: three faults, found in the order they surfaced

### 1. OIDC subject — and a wrong diagnosis first

`git push` warned the repository had moved (`Virtual-Verbal-Assistant` →
`ProjectECA`), the trust policy on `GitHubActionsECRRole` named the old repo, and
every `Deploy Agent Image` run since **#14 (03-09)** had died at
`configure-aws-credentials`. The story fit. It was wrong.

Renaming the subs changed nothing. The actual claim GitHub presents is:

```
repo:Beginner-Mon@142661626/ProjectECA@1057715951:ref:refs/heads/release
```

— owner and repository **IDs** appended. No name-only pattern could ever have
matched it.

CloudTrail is what settled it. The `AssumeRoleWithWebIdentity` denial records the
`sub` that was presented, and it is the only place the full string appears —
GitHub's own logs need repository admin:

```bash
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=AssumeRoleWithWebIdentity
```

The policy now lists both forms. The ID form is the better half: it survives
renames, and a repository re-created under an old name gets a new ID, so it
cannot inherit the right to publish images.

### 2. `lambda:GetFunctionConfiguration` — red runs over successful deploys

With OIDC fixed, `build-and-push` went green and the run failed one step later,
at `Update the function code` — in three seconds.

`update-function-code` **succeeded**. `aws lambda wait function-updated` then
called `GetFunctionConfiguration`, which `VvaAgentDeploy` did not grant.
CloudTrail shows the same denial at `2026-09-05T08:36:49Z` and at
`2026-08-29T10:55:40Z` — run #13, the last deploy anyone believed had failed.

So the pipeline has been **reporting failure on deploys that worked**, and
skipping the smoke test that would have caught a genuinely broken image. Added
the action to the inline policy, and ran the skipped smoke test by hand:
`StatusCode 200`, no `FunctionError`, `{"status":"ok"}`.

The lesson is in the workflow comment now: *when an agent deploy fails, check ECR
for the sha before reading anything else.*

### 3. Amplify service role — UNRESOLVED

`BUILD` fails 0.3s after the compute is provisioned:

```
!!! Unable to assume specified IAM Role.
```

What was checked and found unchanged: trust policy (`amplify.amazonaws.com`,
`sts:AssumeRole`, no conditions), no permissions boundary, both managed policies
attached, no `UpdateApp` touching the role since 20-08, role untouched since it
was created on 15-08. Re-binding the same ARN did not help.

The one hard clue: `RoleLastUsed` is **2026-08-29T12:05:34**, which is job 27 —
the last build that succeeded. Nothing in IAM or the app config changed after it.

The app is also using `AmplifySSRLoggingRole` as its service role, which is
anomalous for this purpose, and no Console service role
(`AdministratorAccess-Amplify`) exists in the account at all. Owner is creating
one through **App settings → General → Service role → Create and use a new
service role**, which is the supported path.

## Production state at end of session

| | Running | |
|---|---|---|
| Backend Lambda | `f296f2b` | ✅ smoke 200; `/characters/anne` returns both `en` and `vi` |
| Frontend Amplify | `352e1cf` (29-08) | ❌ blocked on the service role |
| `characters` rows | new overlay shape | ✅ no "Ordinary" |

**The mismatch is visible to users.** The deployed frontend does
`character?.ui_strings ?? {}` and merges per key; against the new
`{en:…, vi:…}` shape nothing matches, so every greeting falls back to
`FALLBACK_UI_STRINGS` — generic, character-neutral Vietnamese. It also sends no
`locale`, so `ChatRequest.locale` defaults to `"en"` and safety templates come
back in English.

**Rolling the Lambda back does not help.** The old loader against the new rows
gives `voice` empty outright; the current state is the better of the two. The
way out is forward.

# 05-09-2026 — the personas ship, and four deploy faults stacked behind each other

> Previous session: [[03-09-2026]]. Plan: [[preferences-v3-plan]].

## Summary

Owner rewrote `personas/anne/vi.md`; `en.md` was rewritten against it, the
library was renamed from Ordinary to ECA everywhere it still mattered, and every
greeting stopped opening with an exercise. That part took twenty minutes.

Getting it to production took the rest of the session and uncovered four separate
faults, every one of them dating from the same week and each hiding the next.
Nothing had reached production since **29-08** and nobody knew, because each
failure reported something other than itself. Both halves are now live and
verified.

Two of the four were misdiagnosed first, and both times the wrong answer was the
plausible one — the repository rename explained the timing perfectly and was not
the cause of the fault it was blamed for. What broke the deadlock each time was
the same move: stop reading the error message and go find the record of what
actually happened. CloudTrail had both answers.

Roles stayed swapped — K implemented.

## What changed in the personas

**The library.** `anne/_core.md` had said ECA since the overlay split, but the
row the backend actually reads still said *"Retrieved results ARE Ordinary's
library"*. `preload_personas_from_db` fills the cache from `characters.persona`,
and that JSONB **shadows the markdown** — so the agent was citing a source no
grep in this repo could find. Fixed by syncing, not by editing.

"Ordinary Studio" stays on the About page. That is the company; only the library
was wrong.

**The greetings.** Twelve of sixteen prescribed an activity — *warm up, loosen
up, wind down, one relaxing stretch* — before the user had said a word. A
greeting is precisely the moment you cannot know that exercise is what someone
came for. They now follow `anne/vi.md`: name, then one open question. Bronya
keeps one symptom-led slot because for her that IS the open question.

The `(chat)` one-shot examples moved with them. Leaving *"what are we working on
today?"* there would have put the prescribing opener straight back into the
reply.

## `sync_personas_to_db.py` was blind where it mattered

`diff_sections` reports overlay changes under a composite **label** —
`"vi.examples"` — and the printer looked that label up as a **key**.
`persona.get("vi.examples")` is always `None`, so every overlay section printed:

```
vi.examples
  - (empty)
  + (empty)
```

Core sections printed correctly, which is exactly why it survived: the report
looked like it worked. The script exists so that nobody writes to
`characters.persona` blind, and it was failing at that, silently. Also taught it
to read a pre-overlay flat row as the `vi` overlay, so this migration's report
did not understate what it was replacing.

## Deploy: three faults, found in the order they surfaced

### 1. OIDC subject — and a wrong diagnosis first

`git push` warned the repository had moved (`Virtual-Verbal-Assistant` →
`ProjectECA`), the trust policy on `GitHubActionsECRRole` named the old repo, and
every `Deploy Agent Image` run since **#14 (03-09)** had died at
`configure-aws-credentials`. The story fit. It was wrong.

Renaming the subs changed nothing. The actual claim GitHub presents is:

```
repo:Beginner-Mon@142661626/ProjectECA@1057715951:ref:refs/heads/release
```

— owner and repository **IDs** appended. No name-only pattern could ever have
matched it.

CloudTrail is what settled it. The `AssumeRoleWithWebIdentity` denial records the
`sub` that was presented, and it is the only place the full string appears —
GitHub's own logs need repository admin:

```bash
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=AssumeRoleWithWebIdentity
```

The policy now lists both forms. The ID form is the better half: it survives
renames, and a repository re-created under an old name gets a new ID, so it
cannot inherit the right to publish images.

### 2. `lambda:GetFunctionConfiguration` — red runs over successful deploys

With OIDC fixed, `build-and-push` went green and the run failed one step later,
at `Update the function code` — in three seconds.

`update-function-code` **succeeded**. `aws lambda wait function-updated` then
called `GetFunctionConfiguration`, which `VvaAgentDeploy` did not grant.
CloudTrail shows the same denial at `2026-09-05T08:36:49Z` and at
`2026-08-29T10:55:40Z` — run #13, the last deploy anyone believed had failed.

So the pipeline has been **reporting failure on deploys that worked**, and
skipping the smoke test that would have caught a genuinely broken image. Added
the action to the inline policy, and ran the skipped smoke test by hand:
`StatusCode 200`, no `FunctionError`, `{"status":"ok"}`.

The lesson is in the workflow comment now: *when an agent deploy fails, check ECR
for the sha before reading anything else.*

### 3. The Amplify error that was not about IAM

`BUILD` failed 0.3s after the compute was provisioned:

```
!!! Unable to assume specified IAM Role.
```

Taken at face value, that cost four builds. Trust policy, permissions boundary,
attached policies, `UpdateApp` history — all checked, all unchanged since the
role was created on 15-08. Re-binding the same ARN did nothing. A **brand new
role**, trusting `amplify.amazonaws.com` with `AdministratorAccess-Amplify` and
`AmplifyBackendDeployFullAccess`, failed identically. That is what finally ruled
the role out.

The evidence that settled it: **CloudTrail holds no `AssumeRole` event for
either role.** Not a denial — nothing. Amplify never called STS. The message
names IAM for a failure that happens before any of it.

The actual fault was the repository connection. The app still held:

```
repository: https://github.com/Beginner-Mon/Virtual-Verbal-Assistant   ← old name
clone:      TOKEN
```

`update-app --repository` refuses without a token, so it is a Console action:
**App settings → General → Repository → Reconnect repository**. That also moved
the app off the OAuth token onto the GitHub App.

The timing had said this all along, and the same rename that misled §1 was the
real cause here: last green build **29-08 12:00 UTC**, rename between 29-08 and
03-09, every build since dead at provisioning. A second symptom pointed the same
way and was written off as noise — **pushes to `release` stopped triggering
builds**, and all five runs this session had to be started by hand. The webhook
died with the clone. It fired on its own the moment the repository was
reconnected.

`AmplifyHostingServiceRole-ProjectECA` was created on a wrong hypothesis and is
kept anyway: using `AmplifySSRLoggingRole` as an app's service role was odd, and
the old role is still there to switch back to.

### 4. A TypeScript error, hidden behind fault 3

With the clone fixed, the build reached `npx ampx pipeline-deploy` and failed on
five `TS2322`s in `amplify/functions/pre-token-generation/handler.ts`.

`ee71f4a` (**30-08**) changed the DynamoDB row from `Record<string, any>` to
`Record<string, unknown>` and typed the Cognito event — correct, but
`claimsToAddOrOverride` is `Record<string, string>`, so five claims went from an
implicit coercion under `any` to a hard error. It was pushed **the day after the
last green build**, into a pipeline that had already stopped being able to
report anything.

Claims now cross that boundary through a `claim()` helper: absent and null
become `''` rather than the string `"undefined"` a bare `String(value)` would
have written into a live token, and `custom:appUserId` falls back to
`cognitoSub` for the same reason the not-found branch already does.
`set-password` had the same shape of gap — `event.requestContext.authorizer`
where `requestContext` is optional — which would have turned a clean 401 into a
500.

Verified locally before pushing (`tsc --noEmit -p amplify/tsconfig.json` and
`npm run build`, both clean) rather than by burning another build cycle.

## Production state at end of session

| | Running | |
|---|---|---|

| Frontend Amplify | `25df873` (job 34) | ✅ BUILD / DEPLOY / VERIFY all green |
| `characters` rows | new overlay shape | ✅ no "Ordinary" |

The deployed bundle was checked for the Phase 1 work rather than assumed:
`eca-locale`, `Tiếng Việt` and the i18n runtime are all present in
`assets/index-B82iw0qg.js`, and the site answers 200.

For the ~35 minutes between the two deploys, production ran the new backend
against the 29-08 frontend. That frontend does `character?.ui_strings ?? {}` and
merges per key, so against the new `{en:…, vi:…}` shape nothing matched and every
greeting fell back to `FALLBACK_UI_STRINGS`; it also sent no `locale`, so safety
templates came back in English. Rolling the Lambda back would have been worse,
not better — the old loader against the new rows empties `voice` outright.

**Deploy order, for next time:** frontend first. It was planned that way and the
plan did not survive contact — both targets fire from a single push to `release`,
so the ordering is not actually controllable from git, and here the backend won
because Amplify was broken.

# 19/05/2026 — Architecture Planning: VVA LangGraph Re-Architecture

## Summary

Full-day architecture planning session for re-architecting VVA from a custom hand-rolled agent framework to a LangGraph multi-agent supervisor system. Produced Plan v1, received critical review from N, revised to Plan v2. Key decisions locked; some deferred to implementation.

---

## 1. Codebase Review (K)

K reviewed the entire codebase to build context before planning:

**Current stack identified:**
- AgenticRAG: Custom orchestrator (780 lines), Gemini 2.5-Flash, ChromaDB, Double-RAG, HyDE
- DART text-to-motion: Diffusion model on WSL/CUDA, port 5001, existing MCP server
- SpeechLLm: Whisper STT + Coqui/ElevenLabs TTS, port 5000
- ECA UI: HTML/JS + partial React, port 3000
- Infrastructure: Docker (ChromaDB), Redis (Celery), Firebase (sessions), 4+ Conda envs

**Key observation:** D1-D9 refactor (May 2026) added circuit breakers, tracing, tool registry, and vector backend abstraction — providing a solid foundation for the rewrite.

### Round 4 — Detailed Agent Graph (Owner's vision)
Owner provided detailed agent architecture:

- **ManagerAgent**: Lightweight routing + aggregation. NOT heavy reasoning.
- **ReasoningAgent**: Separate from Manager. Handles complex multi-step analysis.
- **RetrievalAgent**: Still needed even with Claude API (domain-specific docs, clinical guidelines, HumanML3D library).
- **MemoryAgent**: Split long-term (conversations in DB) + short-term (patterns, preferences in Redis). Use case: remembering user's back pain history to avoid certain exercises.
- **MotionAgent**: Interface with DART for 3D motion generation.
- **SpeechAgent**: Interface with TTS for audio synthesis.
- **ConversationAgent**: Multiple personality MD files, each with matching UI avatar. Applies persona styling to responses.

**Streaming**: WebSocket for text, output mode toggle (text/speech/both).
**MCP catalog**: Start simple, grow to marketplace later.
**Tenancy**: Single-user first.

## 3. Plan v1 Produced

K produced comprehensive architecture plan with:
- 7 LangGraph nodes (Manager, Memory, Retrieval, Reasoning, Motion, Conversation, Speech)
- MCP for DART and TTS
- MongoDB replacing Firebase, ChromaDB kept
- Dual streaming (WebSocket + SSE)
- Celery removed, replaced by LangGraph async
- 6-phase implementation over 10 weeks

## 4. N's Critical Review (Simulated Peer Review)

N raised 4 major objections against Plan v1:

### Objection 1: LangGraph = "Black Box" replacing controllable code
- **Concern**: State mutation debugging, vendor lock-in, LangChain breaking changes
- **Alternative proposed**: Refactor `api_orchestrator.py` with Strategy/Chain of Responsibility pattern
- **K's response**: Acknowledged vendor lock-in risk. Defended LangGraph for built-in streaming, checkpointing, parallel execution, graph visualization. Counter-proposal: keep node logic as pure Python functions with zero LangGraph imports inside — framework is wiring, not logic.
- **Resolution**: **LangGraph kept**, but with framework-agnostic node design

### Objection 2: MCP for internal services = Over-engineering
- **Concern**: DART and TTS are internal microservices. MCP adds latency, serialization overhead, deployment complexity. End users (physical therapy patients) don't need to configure MCP servers.
- **K's response**: **Agreed 100%.** MCP for internal services is wrong.
- **Resolution**: **DART/TTS → direct REST calls.** MCP deferred to future phase for external third-party tools only.

### Objection 3: Removing Celery & Firebase = Ops risk
- **Celery concern**: Celery has retry, DLQ, worker monitoring. LangGraph async is just Python event loop — no persistence, no retry on crash.
- **Firebase concern**: Why migrate from a managed service to self-hosted MongoDB?
- **K's response**: Agreed on Celery — keeping it. Firebase discussion escalated to Owner.
- **Resolution**: **Celery kept** for async background tasks. Firebase → discussed further (see below).

### Objection 4: Streaming & flow design concerns
- **Dual transport concern**: WebSocket + SSE = 2 connections, race conditions, frontend complexity.
- **Manager vs Reasoning concern**: 2 sequential LLM calls increases latency for complex queries.
- **K's response**: Agreed on single WebSocket. Defended Manager/Reasoning separation with latency analysis (simple queries skip Reasoning), but agreed to profile in Phase 1.
- **Resolution**: **Single WebSocket for everything.** Manager/Reasoning separation kept but will merge if profiling shows >500ms Manager latency.

## 5. Owner's Additional Decision: PostgreSQL

Owner proposed **PostgreSQL (pgvector)** instead of MongoDB or Firebase:
- Replaces Firebase Firestore (conversations, profiles)
- Replaces ChromaDB (vector embeddings via pgvector extension)
- Consolidates 3 data stores (Firebase + ChromaDB + Redis) → 2 (PostgreSQL + Redis)

**K's assessment**: Excellent choice. pgvector is production-proven for vector search at this scale. Single backup strategy. Runs local in Docker.

## 7. Architecture Decisions Log (ADR)

### ADR-001: Use LangGraph for agent orchestration
- **Status**: Accepted (with de-risk strategy)
- **Context**: Need to replace 780-line monolithic orchestrator
- **Decision**: LangGraph StateGraph with pure Python node functions
- **Consequences**: Vendor dependency on LangChain ecosystem; mitigated by keeping node logic framework-agnostic

### ADR-002: PostgreSQL (pgvector) as unified data store
- **Status**: Accepted
- **Context**: Currently using Firebase + ChromaDB + Redis (3 stores)
- **Decision**: PostgreSQL replaces Firebase and ChromaDB. Redis kept for STM + Celery.
- **Consequences**: Need migration script. pgvector performance must be benchmarked against ChromaDB in Phase 2.

### ADR-003: Direct REST for internal services, MCP for future extensions only
- **Status**: Accepted
- **Context**: Originally planned MCP for DART/TTS calls
- **Decision**: DART/TTS called via httpx (direct REST). MCP reserved for future third-party tool integrations.
- **Consequences**: Simpler architecture, lower latency. MCP infrastructure deferred.

### ADR-004: Keep Celery for async background tasks
- **Status**: Accepted
- **Context**: Originally planned to replace Celery with LangGraph async
- **Decision**: Celery retained. LangGraph handles sync agent graph; Celery handles async background work (motion rendering, TTS, doc indexing).
- **Consequences**: Two async systems coexist. Clear separation: LangGraph = request-scoped, Celery = background jobs.

### ADR-005: Single WebSocket for all client-server streaming
- **Status**: Accepted
- **Context**: Originally planned WebSocket (text) + SSE (events)
- **Decision**: Single WebSocket with JSON payload types (token, motion_ready, speech_ready, error, done)
- **Consequences**: Simpler frontend, no race conditions. Celery → Redis pub/sub → WebSocket bridge needed.

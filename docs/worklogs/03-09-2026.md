# 03-09-2026 — ADR-008: preferences fold into `users`, and the route to production

> Plan: [[preferences-v3-plan]] — supersedes [[user-preferences-plan]] and
> [[character-lite-optimization-plan]]. Yesterday's work: [[01-09-2026]].

## Summary

Design review of the two plans merged on 01/09, then the reversals it produced.
Neither feature could have worked outside localhost; that is the half of this
that is not a design change.

None of it is deployed. Every commit involved is on `feat/user-preferences`;
`origin/main` and `origin/release` contain none of them, and today's work is not
even committed. So the reversals below cost a migration and a rebase, not a
rollback — which is the whole reason for doing them now.

Roles were swapped for this session at the Owner's instruction — K implemented
rather than handing the plan to N.

## ADR-008

| # | Decision | Why |
|---|---|---|
| D1 | Drop `user_preferences`; one `users.preferences JSONB` column | Strictly 1:1. `users` already had the RLS policy and grants (007), a row created in five code paths, and `DELETE FROM users` in `db/gdpr.py`. The second table bought a second policy, a JOIN, a seed step that made GET write, and a third copy of `display_name` |
| D2 | Everything in the JSONB — no typed columns | Preferences are an open set. A typed column per setting is a migration per setting; a field in `SyncedPrefs` is neither |
| D3 | No foreign key on `selected_character_slug` | The catalog soft-deletes, so `ON DELETE SET NULL` never fires, and `slug` is stable so `ON UPDATE CASCADE` buys nothing. The app-level check is strictly stronger than the FK was |
| D4 | No colour enum anywhere but `avatarPalette.ts` | Was three places (CHECK constraint, Pydantic `Literal`, palette). Frontend and backend deploy independently, so a colour released to the UI first would 422 for whoever picked it |
| D5 | Drop the `version` optimistic lock; last write wins | The merge is per key. Two devices changing two different preferences never disagreed, and the 409's resolution was always "take the other write" |
| D6 | PHI guard is `extra="forbid"`, not a keyword blocklist | The blocklist checked five names at the top level only. `{"a": {"injury_history": …}}` and `{"note": "thoát vị L4"}` both passed |
| D7 | Restore `SELECT 1 FROM characters WHERE slug=$1 AND is_active` | After D3 this is the only guard, and it was always the only one that could see `is_active` |
| D8 | `theme` and `graphics.*` stay device-local | Owner's call, reaffirmed. Q3 answered it for graphics; the FOUC fix stays inside that boundary |
| D9 | `display_name` leaves the preferences API | Cognito owns it — `ProfileContent.tsx` reads `custom:displayName` from the token. `users.display_name` and `user_preferences.display_name` were copies nobody read |
| D10 | Keep `/me/preferences`, keep two serial requests on load | The URL maps to one column. The next step is a 9-17 MB VRM download, so a second round trip is noise, and `/characters/{slug}` keeps its public 5-minute cache |

Q4 in the v2 plan is recorded as "chốt" but the Owner never answered it — §2 of
that plan says so and §3 promotes the inference to a decision anyway. D8 is that
question actually being asked and answered.

## Changes

### Schema
- `alembic/versions/010_preferences_into_users.py` — new. Adds
  `users.preferences JSONB`, carries 009's rows across with
  `jsonb_strip_nulls(jsonb_build_object(...)) || p.prefs`, drops the policy,
  index and table. `downgrade()` rebuilds 009 and unpacks the column back,
  coalescing any colour 009's CHECK would reject.

### Backend
- `api/schemas.py` — `SyncedPrefs` with `extra="forbid"` replaces the
  `AvatarBg` Literal and the flat fields. `UserPreferencesOut`/`Patch` carry
  `preferences` and nothing else.
- `api/routes_preferences.py` — rewritten. `_validate_prefs`,
  `ALLOWED_AVATAR_BG`, the size/depth/prototype limits and the PHI blocklist are
  all gone; the model does that work. GET is one SELECT and creates nothing.
  PATCH is one UPDATE with `preferences || $2::jsonb`, guarded by the `is_active`
  check, with the string-matched `"foreign key"` handler removed.
  `_read_prefs` parses stored objects leniently — strict on write, forgiving on
  read, so one stale row cannot 500 for one user.

### Infrastructure
- `infra/infra/rest_api_stack.py` — `GET`/`PATCH /me/preferences` under the
  existing `me` resource with the Cognito authorizer. This is the 403 that was
  waiting to happen on the first deploy.
- `infra/lambda/characters/handler.py` — `_PUBLIC_COLUMNS_LITE` for the list
  response, matching the FastAPI shim. Production finally gets the narrowing
  that was measured and merged on 01/09.

### Frontend
- `contexts/PreferencesContext.tsx` + `hooks/usePreferences.ts` — new. One
  `GET /me/preferences` per load, provided to everyone. Outside `MotionProvider`.
- `lib/preferences.ts` — new shape; the module cache and the shared in-flight
  promise are gone along with the `AbortSignal` parameter that made one
  consumer's unmount cancel the others' fetch.
- `hooks/useUserPreferences.ts` — revived, not rewritten. Kept its debounce,
  `visibilitychange` refresh and rollback; dropped the 409 branch. Pending
  patches now accumulate rather than replace, so a colour and a character picked
  within 300ms both survive.
- `contexts/AvatarBgContext.tsx`, `contexts/MotionContext.tsx`,
  `components/panels/AvatarsPanel.tsx` — read from the provider. The version
  bookkeeping, the per-component `fetchAuthSession` calls and the 409 handling
  all disappear with it.
- `contexts/ThemeContext.tsx` — initial theme now read from the class the
  blocking script already put on `<html>`. One place decides it, so React cannot
  disagree with the paint that already happened.
- `hooks/useAvatarBg.ts` — new, splitting the hook out of the context file the
  way `useMotion` and `useTheme` already are.

### Tests
- `tests/langgraph_agents/test_preferences.py` — rewritten, 17 tests. Several
  lock a specific past mistake: nested PHI must be rejected,
  `avatar_bg: "neon"` must be **accepted** (an enum reappearing in the backend
  is the regression), GET must call no `execute`, and the source must contain no
  `version + 1`, `AND version` or `409`.
- `tests/infra/test_characters_contract.py` — new. Parses both `/characters`
  implementations with `ast` and asserts their column lists match. The two
  cannot import each other — the Lambda ships as a CDK asset directory
  containing only itself — so this is what stops them drifting again.
- `src/hooks/useTheme.test.ts` — new, 7 tests. The initial-theme decision came
  out of `ThemeContext.tsx` into `resolveInitialTheme(root, stored, default)` so
  it could be tested without a DOM (vitest runs in the `node` environment here,
  and jsdom is not installed — adding it would touch the pinned lockfile). The
  first test is the regression itself: no stored value, `defaultTheme: 'light'`,
  `<html class="dark">` → must be `dark`.

# Session pointer: written when there is something to point at, and expiring

Second piece of work, prompted by a 404 the Owner spotted in the console while
checking the above.

## The fault

Every clean page load sent one request that could only ever 404:

```
localStorage empty
  → loadOrCreateSessionId() minted a UUID and stored it immediately
  → the mount effect asked GET /sessions/{the id it had just invented}
  → 404
```

The `conversations` row is written server-side on the first turn
(`db/session_store.py`, `INSERT … ON CONFLICT (session_id) DO UPDATE`), so the
gap between "a pointer exists" and "a row exists" always answered 404. Pressing
**new chat** and walking away stored an id no message ever followed — and that
one 404'd on every load from then on, permanently.

Confirmed against Neon rather than assumed: `19c6ccde-25ed-401c-ac34-9f1f15c62f26`
sat in that browser's localStorage and **existed in `conversations` for no user
at all**, while the account's seven real conversations were untouched.

`ChatContext.tsx` already knew — `if (status !== 404) console.warn(...)` — but
swallowing it in the app does not silence the browser's own network log. The
only way to stop the noise is to not send the request.

And the pointer had no expiry of any kind: localStorage does not expire, and
nothing in the app cleared this key, not even on sign-out.

## Decisions (ADR-009)

| # | Decision | Why |
|---|---|---|
| S1 | Write the pointer **late** — only when a message is sent | Closes the window the 404 lived in. No pointer, no request |
| S2 | **TTL of 2 hours**, re-stamped on every send | Owner asked for 1–2h; the upper end so lunch or a meeting still resumes. The clock runs from the last message, not from the start, so an active conversation never expires mid-use |
| S3 | TTL is **client-side** | It governs whether a refresh *resumes*, not whether a conversation can be *opened*. Picking an old one out of the sidebar must keep working however old it is, so `GET /sessions/{id}` is untouched |
| S4 | Keep auto-resume rather than drop it | Losing your place on an accidental F5 is a real regression; that is what the mechanism is for |
| S5 | Discard the legacy bare-string value | Its age is unknowable and it may be one of the pointers that never had a row — exactly the case found. Nothing is deployed and there are six dev users, so the cost is one lost resume, once |
| S6 | Clear the pointer on sign-out | A pointer into account A's conversation was surviving into account B. Harmless only because `GET /sessions/{id}` filters by the token's user and answered 404 — the noise being removed |

No backend change. The server still accepts a client-minted id and creates the
row on the first turn.

## Changes

- `src/lib/chatSession.ts` — new. `readSessionPointer` / `stampSessionPointer` /
  `clearSessionPointer`, with `now` and `storage` as parameters so the rules test
  without a DOM (vitest runs in the `node` environment; jsdom is not installed
  and adding it would touch the pinned lockfile). Storage is `{"id","at"}`;
  expiry is enforced on read — lazy, the way Redis expires most keys — because
  localStorage will never do it for us.
- `src/contexts/ChatContext.tsx` — `loadOrCreateSessionId` gone (it was being
  called **twice** in render). `sessionIdRef` and `activeSessionId` are now
  `string | null`. The mount effect returns early when there is no pointer,
  **calling `setIsRestoring(false)` on the way out** — that flag is cleared in a
  `finally`, so returning without it would leave it true forever and the greeting
  effect, which waits on it, would never run. `startNewSession` clears the
  pointer instead of minting one. The single send site calls `ensureSessionId()`,
  now the only place an id is created.
- `src/hooks/useChat.ts`, `src/components/panels/ChatSessionsPanel.tsx` — the
  widened type. The `s.session_id === activeSessionId` comparison needed no
  change: `null` matches nothing, so no row highlights when there is no
  conversation, which is correct.
- `src/components/AuthGuard.tsx` — `clearSessionPointer()` alongside the Amplify
  key purge.

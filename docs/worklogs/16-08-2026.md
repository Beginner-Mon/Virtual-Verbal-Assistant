## 1. ADR-006: Hai track hạ tầng

**Status**: Accepted (16/08/2026, Owner)

**Context**: App cutover Neon 31/07. CDK vẫn provision RDS + RDS Proxy + Lambda
trong VPC private isolated — kiến trúc chuẩn doanh nghiệp, nhưng chưa từng
deploy và tốn tiền ở nhiều tầng: RDS instance + storage, RDS Proxy theo
vCPU-hour, và interface VPC endpoint (~$7/tháng mỗi cái mỗi AZ) cho mọi AWS
service mà Lambda trong isolated subnet cần gọi. Các interface endpoint đã bị
xoá khỏi `vpc_stack.py` vì lý do đó.

**Decision**: Giữ song song hai track trong CDK, chỉ khác cái nào được synth.

- **Track 1 (production, đóng băng)**: API Gateway → Lambda in-VPC → RDS Proxy →
  RDS. Không deploy, không sửa. Opt-in bằng `CDK_ENABLE_TRACK1=1`.
- **Track 2 (tối ưu chi phí, hoạt động)**: CloudFront → Lambda Function URL
  ngoài VPC → Neon. Không NAT, không RDS Proxy, không interface endpoint.

**Consequences**:

- DB không còn được VPC che. Bù bằng TLS + DSN trong SSM SecureString + Function
  URL `AWS_IAM` (chỉ CloudFront OAC gọi được).
- `cdk deploy --all` trở thành thao tác nguy hiểm — nó sẽ dựng RDS. Đã guard
  bằng `CDK_ENABLE_TRACK1` và ghi cảnh báo đầu `infra/README.md`.
- Lambda ngoài VPC gọi SSM qua đường internet thông thường → **không phát sinh
  interface endpoint nào**, đúng cái tầng chi phí đã khiến chúng bị xoá.
- Điểm phản trực giác cần ghi: với Neon, **bỏ Lambda ra khỏi VPC là rẻ VÀ nhanh
  hơn** (không $32/tháng NAT, không attach ENI lúc cold start). Đưa vào VPC "cho
  an toàn" ở đây là trả tiền để chạy chậm hơn.

**Ghi chú về đánh số**: repo đang có ba hệ ADR song song — `ADR-001..005`
(worklog 19-05), `D1–D33` (`docs/plans/reupdate-plan.md`), `D1–D6`
(`.claude/plans/character-identity-system.md`). Ba hệ dùng chung tiền tố `D` và
đánh số chồng nhau. Tôi tiếp `ADR-006` theo tiền lệ worklog. **Cần Owner quyết
có gom về `docs/adr/` không** — chưa làm vì đó là quyết định về quy ước, không
phải về code.

## 4. Track 2: Lambda + CloudFront

### 1 Lambda + Function URL, không phải 3 Lambda + API Gateway

Phương án trình Owner ban đầu là 3 Lambda + API Gateway (theo pattern
`infra/lambda/*` đã có). Tôi rút gọn còn 1 Lambda + Function URL:

CloudFront cache catalog ở edge, catalog có đúng 4 dòng và gần như không đổi →
origin bị gọi cỡ 1 lần mỗi TTL. Mọi ưu điểm per-request của API Gateway trở nên
vô nghĩa. Ba route cũng là ba cách đọc **cùng một resource**, không phải ba
operation khác nhau như `list`/`delete`/`resume` của session.

Owner đã được thông báo và có thể yêu cầu quay lại pattern cũ.

### `shared/db.py` — hai mode, một file

Thêm nhánh `DB_MODE=neon|rds`. Mode `neon` đọc một SSM SecureString chứa DSN,
parse thành kwargs rời (pg8000 không nhận URL). Bỏ `generate_db_auth_token` và
`rds-db:connect` ở nhánh đó.

**Giữ nguyên** connection cache module-level + liveness check (đúng cho Lambda
warm reuse) và `ssl.create_default_context()` (Neon dùng CA chuẩn). Fork file sẽ
để lại hai bản cache và hai bộ serializer phải giữ đồng bộ — không làm.

Credential được percent-decode: mật khẩu Neon thường xuyên chứa ký tự bị escape
trong URL, không decode là gửi sai mật khẩu lên server.

### CORS ở CloudFront, không ở S3

Browser chỉ nói chuyện với CloudFront; CORS config của S3 không bao giờ được
thấy. Draft plan §3.2 đặt ở S3 vì giả định bucket public-read — đã sửa.

### Key băm nội dung

`characters/{slug}/{sha256[:8]}.vrm`. Đổi model = đổi key = đổi URL trong DB →
không bao giờ cần invalidation, và cache policy đặt `immutable, max-age=1 năm`.

Catalog thì ngược lại — URL không có hash nên dùng TTL 5 phút để một lần seed
hiện ra được mà không phải invalidate. Ghi kèm cảnh báo: nếu sau này thêm gating
per-user vào `/characters`, TTL này phải bỏ hoặc chuyển cache-by-header.

## 6b. Deploy — đã chạy thật (cùng ngày, sau khi có AWS credentials)

Owner xác nhận máy có credentials → chạy trọn runbook. Account `244203483654`,

### Hai lỗi thật tìm ra trong lúc deploy

**(1) CDK thiếu `lambda:InvokeFunction` cho OAC.** CloudFront → Function URL trả
403 dai dẳng. Loại trừ dần: handler chạy tốt (invoke trực tiếp), IAM auth của
Function URL tốt (tự ký SigV4 → 500 SSM), OAC nói chung tốt (đường S3 qua
CloudFront → 200), routing đúng (403 là JSON của Lambda, không phải XML của S3),
không phải propagation (6+ phút), không phải compression.

Nguyên nhân: **từ 10/2025 Function URL cần cả `lambda:InvokeFunctionUrl` lẫn
`lambda:InvokeFunction`**, mà `FunctionUrlOrigin.with_origin_access_control()`
chỉ cấp cái đầu. Thứ làm nó tốn công là mọi cấu hình đều *trông* đúng, và request
tự ký lại chạy — vì IAM user `admin` vốn có cả hai action. Đã thêm `CfnPermission`
vào `asset_stack.py`; xoá permission thủ công → 403 trở lại → deploy CDK → 500,
xác nhận đúng nguyên nhân.

**(2) `asyncpg` không chạy được migration nhiều câu lệnh — đây là lý do thật khiến
`004` chưa bao giờ áp được.** §0 ghi nhận billing thiếu bảng nhưng chưa biết vì
sao. Chạy migration mới lòi ra:

```
asyncpg.exceptions.PostgresSyntaxError:
cannot insert multiple commands into a prepared statement
```

`004` gộp `CREATE TABLE` + `COMMENT` + `CREATE TABLE` + `COMMENT` vào một
`op.execute()`. Nó **không thể chạy**, chứ không phải ai đó quên. `002` thoát vì
có helper `_split_sql()`; `003` thoát vì chỉ có đúng một câu lệnh. **`005` của tôi
mắc y hệt.** Đã tách cả hai thành mỗi câu một `op.execute()`, kèm comment giải
thích để lần sau không ai viết lại như vậy.

> Sửa một migration đã commit vốn là điều nên tránh. Ở đây chính đáng: `004`
> chưa từng áp thành công ở đâu, và nội dung nó là `CREATE TABLE IF NOT EXISTS`
> nên idempotent.

**(3) Lỗi thiết kế của tôi: S3 prefix đụng đường API.** Plan ghi key
`characters/{slug}/{hash}.vrm` trong khi behavior CloudFront là `/characters*` —
nên request VRM đi vào Lambda, router thấy segment thứ ba không phải
`avatar-profile` và trả 404. Đổi prefix sang `models/`, xoá 4 object đặt sai, seed
lại. Verification bắt được, không phải review.
